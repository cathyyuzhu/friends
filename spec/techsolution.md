# Tech Solution

## 技术栈
- Python
- Anthropic API（`ANTHROPIC_API_KEY`，见 `.env.example`）
- Telegram Bot API（`telegram_bot.py`，各人设独立 token：`TG_TOKEN_<人设ID大写>`）

## 架构
```
personas.json                          人设定义（名字、性格、话痨程度、兴趣）
chat_engine.py                          共享调度核心：接话决策、主动冒泡逻辑、真实历史检索
main.py                                 终端 MVP，本地跑，验证核心机制
telegram_bot.py                         Telegram 群版，每个人设是独立 bot 身份
import_history.py                       把导出的微信聊天记录导入成某个人设的真实历史记忆
data/chat_log.json                      群聊模式的共享聊天记忆
data/chat_log_<persona_id>.json         1 对 1 模式的独立聊天记忆，每个人设一份
data/real_chat_history/<persona_id>.json  某个人设关联的真实微信聊天记录（不进 git，见 .gitignore 里的 data/）
.env / .env.example                     环境变量（API key、Telegram token、群 chat_id）
```

## 关键设计决策
- **终端版和 Telegram 版共用 `chat_engine.py`**：只是输入输出方式不同，核心"谁接话/要不要接话/主动冒泡"逻辑保持一致，避免两处维护
- **接话决策**：谁接话由兴趣关键词是否命中决定（非概率性），话题没人感兴趣时按话痨程度加权兜底，保证不冷场；继续聊几轮则由用户是否参与/参与程度（文本长度、标点）的简单启发式估算（`estimate_continue_rounds`），非模型驱动的人格化决策，先跑通再考虑升级
- **记忆存储**：本地 JSON 文件，无数据库，简单直接；`chat_engine.py` 的 `load_log`/`save_log` 加了可选的 `persona_id` 参数——不传就是群聊共享文件 `data/chat_log.json`，传了就是该人设独立的 `data/chat_log_<persona_id>.json`
- **终端版 1 对 1 模式为什么记忆要单独存**：群聊多人共享一份记忆本来就是设计目标，但排查群聊里"说话人前缀串进回复""角色/归属混乱"这类问题时发现，根源之一是模型在一个塞满多个人设名字的上下文里容易认错人。1 对 1 模式如果还读共享文件，新朋友的 prompt 里会看到别的人设名字，等于没解决问题。所以 1 对 1 模式换成人设独立文件，prompt 里只会出现"我"和当前这一个朋友，从根上减少认错人的概率，而不只是靠 `_strip_speaker_prefixes` 这种后处理兜底
- **Telegram 多 bot 架构**：每个人设注册为独立 bot，其中一个关闭 privacy 模式作为群消息监听者
- **Telegram 私聊 = 1 对 1**：每个人设 bot 本来就能收到直接发给它的私聊消息（跟 privacy 模式无关，那只影响群消息）。监听者 bot 的私聊在它原有的群消息轮询里一并处理（同一个 token，共用一个 offset）；其余 bot 各自开一个独立的轮询任务处理私聊——不能把它们也塞进监听者的轮询，因为 Telegram 的 `getUpdates` offset 是按 bot token 走的，同一个 token 被两个地方用不同 offset 轮询会互相打架、丢消息
- **真实聊天记录导入**：微信没有官方导出 API，约定一个通用中间格式（CSV/JSON，含 时间/发送人/内容），由用户用第三方工具导出后对齐这个格式，`import_history.py` 负责解析、按人设归档、去重追加
- **真实历史检索**：不做摘要/向量检索，先用最简单的字符 bigram 重叠打分，在当前消息和历史记录之间找相关片段注入 prompt——量小时够用，跑通优先于精确

## 部署 / 运行环境
- 本地开发机运行，未做常驻部署
- Telegram 版需要科学上网访问 `api.telegram.org`（国内网络限制）

## 已知架构缺陷（2026-09-16 第一次完整试玩后的诊断）

试玩记录见 `data/chat_log.json`。按"模型 / 架构 / 提示词"分类归因如下。

### 归因一：模型
那次测试实际跑的是 `qwen-flash-character`（`.env` 末尾覆盖了默认值），不是 Claude 也不是 qwen-max。
`qwen-flash` 是最小最快档，`-character` 是角色扮演微调版。由此引发：
- 明令禁止的话照说不误（prompt 里点名禁止的"你想聊什么话题呢"仍然出现）
- 后半段开始输出小说旁白（"（手指摩挲着手机边缘，沉吟片刻）"），这是 `-character` 系列的招牌行为
- 自己给输出加"名字："前缀，甚至串两层（"阿哲: 我: ..."）
**已改为 `qwen-max` 做基线对照。在对照跑完之前，不要把这些症状归因到架构。**

### 归因二：架构（根本问题，换模型治不好）
1. **没有"寻址"概念**：消息是广播的，系统不知道"这句话在对谁说"。`is_mentioned` 只做裸字符串匹配，
   匹配不到就落到按话痨度随机抓人。用户直接问阿哲的问题，可能由音来回答。
2. **人设没有持久状态**：每次调用都是无状态的一次性角色扮演，"我现在在哪、在干嘛"全靠现编，
   编完就扔。同一个人设两分钟内可以既在图书馆走回宿舍、又已经躺在床上。
3. **记忆只有滚动窗口，没有沉淀**：最近 16 条进 prompt，超过 300 条直接丢弃，中间没有任何提炼。
   聊过的事不会变成可长期调用的"关系事实"。
4. **没有沉默权**：`decide_responders` 的设计目标就是"保证一定有人接话"。
   但真实朋友群里大部分消息只有一个人回、很多消息没人回——**永远秒回、永远有人接，本身就是最不像真人的那一点**。
5. **没有时间感**：所有回复在 2~5 秒内产生，没有延迟、没有隔天再提起。

### 归因三：提示词
`build_system_prompt` 写得已经相当细致，但两千多字里绝大部分是"不要做 X"的负面指令。
负面指令堆叠对小模型基本无效，还会稀释注意力。这是典型的**用提示词补架构窟窿**——
`_strip_speaker_prefixes` 那套正则同理，它能删掉前缀，删不掉"音以为自己是阿哲"这件事。

### 业界参照
- **Stanford Generative Agents**：memory stream（带时间戳+重要性评分）+ 按 recency/importance/relevance 检索
  + reflection（定期把零散记忆提炼成洞察）。结论是长期可信的人格**更依赖外部记忆架构而非底座模型**
- **AFA（多用户对话人格混淆）**：结论是"正确的身份路由，而非更复杂的人格建模，才是瓶颈"，
  加身份路由后人格归属准确率 35.7% → 61.3%
- **personagent**：把 PASS（不说话）作为一等公民，管线是 ingest → decide → generate+validate，生成完要过校验才发出
- **turn-taking 研究共识**："什么时候该说话"不是涌现能力，必须显式设计
- **反面参照**：Replika 被评价为"机械复述存储的事实，而不是自然编织进对话"——光存下来不够，得有提炼和自然调用

### 结论：不需要"agent"，需要"有状态的角色 + 调度层"
不需要会调工具、自主规划那种 agent。真正值得 agent 化的只有两处：
**决定谁说话/要不要说话**，和**把聊过的东西提炼成记忆**。其余地方过度 agent 化只会更慢更贵。

改造顺序见 `milestone.md`。当前决策是**主线收敛到 1 对 1**：
身份错乱和抢答是"多人"独有的，而自相矛盾、记忆留不住、回应套路化是单人也一样有的，
后者才是根因且能在单人模式下干净验证。
